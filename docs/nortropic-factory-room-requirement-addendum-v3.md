(Owner-authored addendum, recorded verbatim 2026-08-15. Supplements and is authoritative over any conflicting omission in Product Erratum V2, the original master roadmap, prior SHREDDER prompts, prior final reports and handoffs. Historical artifacts are preserved, not rewritten.)

## 1. SESSION-01 — persistent agent session and ephemeral workspace lifecycle
Distinguish PERSISTENT_ROOM / PERSISTENT_AGENT_SESSION / CONTROLLER_RUN / CONTROLLER_TASK / ATTEMPT / EPHEMERAL_WORKSPACE / PROVIDER_THREAD_OR_SESSION — never interchangeable. Project an equivalent of: room_id, agent_session_id, provider_session_id, run_id, task_id, attempt_id, workspace_id, workspace_generation, workspace_base_sha, candidate_sha, session_started_at, session_last_active_at, session_state, resume_status, last_persisted_evidence_ref, termination_reason. Semantics: a room survives ordinary client/model sessions; an agent session may survive attempt-workspace teardown; an attempt workspace is ephemeral and never canonical authority; bytes existing only in an ephemeral workspace are not durable product state; a candidate becomes durable only through the established exact-candidate path; session reconstruction begins from controller/task/evidence authority, never unverifiable model memory; restart must not duplicate the attempt; unresumable provider sessions produce an explicit classified result; fresh-session fallback retains task/run/candidate provenance; stale sessions cannot issue new effects. Negative controls: reconstructed session trusting model prose as task state → FAIL; deleted workspace treated as publication evidence → FAIL; two sessions resuming one exclusive attempt → FAIL; stale provider thread executing after a successor exists → FAIL; uncommitted sandbox file shown as durable website output → FAIL.

## 2. PARTICIPANT-01 — shared room, multi-participant steering and concurrency
Fields: participant_id, participant_principal, participant_role, client_kind, room_membership_id, membership_state, joined_at, revoked_at, allowed_read_scope, allowed_intention_scope. Roles at minimum OWNER / OPERATOR / OBSERVER / SYSTEM_AGENT — product authorization only where mechanically enforced, never inferred from display labels. Every message/intention attributable to room_id, conversation_id, thread_id, message_id, participant_id, asked_by, client_kind, issued_at. Concurrency: same command from two clients → one effect via command_id/dedup; expected_watermark guards stale steering; a conversational message cannot mutate a frozen current TaskContract; new scope becomes a new intake source/amendment proposal/future task; unauthorized users cannot read private room context; revoked participants lose read+write; Slack display names never impersonate; web and Slack share one room without two truth stores. Negative controls: Slack display name as authenticated identity → FAIL; revoked member still reads → FAIL; concurrent starts create two runs → FAIL; steering silently rewrites frozen TaskContract → FAIL; cross-room participant leakage → FAIL.

Not superseded by showroom or Slack work. ## 4. Room-scoped capability binding
A capability bundle binds: principal_id, bundle_id, bundle_version, room_id or explicit global scope, task_id/run_id where applicable, repository scope, operation scope, network destination scope, credential class, issued_at, expires_at, revoked_at, evidence_ref. Same principal, different capabilities per room. Default deny. Negative controls: bundle from room A used in room B → FAIL; expired/revoked bundle accepted → FAIL; role name grants capability without bundle → FAIL; bundle permits an unlisted repository → FAIL; capability survives revocation via cached success → FAIL.

## 5. CREDENTIAL-PROXY-01 — concrete required control-plane slice
Required effect: authenticated execution principal → current room/run/task/candidate binding → versioned capability bundle → allowed destination → allowed method/operation → minimal short-lived credential or brokered request → result → audit event. The model/client never receives broad reusable raw secrets. Proxy supports: default-deny destinations, short-lived grants, rotation, revocation, replay resistance, task/run binding, destination+operation binding, secret redaction, network-event audit, credential-class audit, fail-closed outage behaviour. No credential value in model context, browser, Slack message, repository, room memory, generic logs or evidence payloads.

## 6. OPERATOR-PROTOCOL-01 — one versioned remote contract
Web, Nortropic Slack, optional Claude Tag, Channels and Routines use ONE Nortropic-owned versioned operator protocol covering: snapshot reads, event/backfill reads, task inspection, evidence reference reads, context reads/writes, typed intention proposal, typed intention submission, command status, notifications, standing-work management. Properties: schema_version, request_id, idempotency_key, authenticated_client_id, room_id, expected_watermark where relevant, issued_at, expires_at, pagination/backfill cursor, result status, typed rejection reason, trace/evidence reference. Behaviour: reconnect loses/duplicates nothing; independent client upgrades within a documented compatibility window; unknown major fails closed; unknown future events inspectable but non-authoritative; explicit rate limiting; client caches never become truth; no adapter invents a sixth intention; no client invents an alternative command-status vocabulary.

## 7. SLACK-INBOX-01 — real remote source intake
Sources: plain text, Markdown code blocks, Markdown file attachments, supported Slack file attachments, thread replies referencing a prior source. Preserve per source: slack_team_id, slack_channel_id, slack_thread_ts, slack_message_ts, slack_event_id, slack_file_id where present, room_id, participant_id, source_ref, source_sha256 claim, content_type, filename, size_bytes. Requirements: Slack request/event identity verified; server-side file download with the app's scoped credential; type/size limits; no semantic compilation in Slack; controller rereads and rehashes per the canonical intake contract; deleted/expired/inaccessible Slack files → explicit rejection; duplicate deliveries → one source/command; edits never silently mutate a stored source (edit = new source version or amendment proposal); message/file content never in generic logs. Before live S10/S13: fixture/fake-transport tests allowed; the complete Slack intake UX and security boundary still built; no live acceptance claimed.

## 8. NOTIFICATION-01 — delivery, acknowledgement and resolution
Records: notification_id, signal_type, severity, room_id, run_id, task_id, dedup_key, created_at, delivery_channel, delivery_status, delivered_at, acknowledged_by, acknowledged_at, snoozed_until, resolved_at, superseded_by, evidence_refs. Statuses at least PENDING / DELIVERED / ACKNOWLEDGED / SNOOZED / RESOLVED / DELIVERY_FAILED / SUPERSEDED. Requirements: no duplicate spam for one condition; resolved never presented active; acknowledgement never changes controller truth; payloads carry references not secrets; model-independent controller alarms work with no model session alive; the conversational Slack client never replaces h-014 alarm semantics; delivery failure visible in Verkstadsgolvet. Quiet hours/escalation = explicit policy, never implicit model judgement.

## 9. STANDING-MANAGEMENT-01
Execution vs administration separated. Narrow management contract: standing_work.create / inspect / update / enable / disable / delete — a SEPARATE versioned contract from the five run/task intentions. Every mutation carries management_command_id, standing_work_id, room_id, authenticated_principal, expected_version, issued_at, expires_at, typed payload, status, rejection reason, evidence_ref. Stale expected_version rejects; duplicates one effect; disabled never fires; deleted cannot resurrect via stale events; update never changes historical runs; standing work only creates proposals/sources/ordinary tasks — never candidate/verdict/attestation/promotion/main writes.

## 11. DATA-GOVERNANCE-01 — showroom, context and audit data
All showroom data synthetic, clearly non-customer (no real names, domains, contacts, credentials or proprietary content in generated fixtures); fixture generation schema-derived; explicit context retention; effective deletion; enforced participant revocation; explicit audit retention (may differ from conversational context); secrets redacted before persistence; personal Slack content stored only per the approved source/context contract; context+audit exportable in readable evidence format; cross-customer/cross-room/cross-channel queries fail closed; production backups respect deletion/retention. Showroom data and production data never silently joined.

## 12. OWNER-ACTION-01 — remote attention is not remote authority
Room/Slack may display owner-attention/owner-authority/external-provisioning/legal-human-only conditions and allow acknowledge, open evidence, copy exact required action, request fresh inspection, snooze per policy. They may NOT treat Slack emoji, button clicks, ordinary web sessions, model confirmations or notification acknowledgements as owner authority — unless a separate owner-action protocol has been threat-modelled, test-authored, frozen, mechanically authenticated, replay-protected, candidate/run/task-bound and independently reviewed. Remote owner-action support is a separate future authority slice; until then owner-only ceremonies remain fail-closed and clearly explained.
